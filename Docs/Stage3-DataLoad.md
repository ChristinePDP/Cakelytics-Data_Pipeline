# Stage 3: Data Load Documentation

**Project:** CakeLytics ETL Pipeline (Aileen & Niculus Cake Shop)  
**Stage:** 3 of 3 (Extraction → Transformation → Load)  
**Implementation Status:** Proposed / Pending Warehouse Integration  
**Target Database:** PostgreSQL (hosted on Supabase)  
**Proposed Target Schema:** `warehouse`  

This document describes the proposed Data Load stage of the CakeLytics ETL pipeline. It defines how the validated and transformed outputs from Stage 2 are transferred into the analytics warehouse, including the target table structures, loading strategy, validation procedures, metadata, retention policies, and failure handling.

The Load stage receives the in-memory Pandas DataFrames `dim_date` and `fact_daily_summary` from Stage 2. It must use only the data and metadata handed over by the Transformation stage. No additional extraction, data cleaning, or business transformation is performed during this stage.

> **Implementation Note:** The Stage 2 documentation identifies the transformation pipeline as a Phase 2 implementation and states that direct warehouse insertion is handled by the subsequent Load stage. Since the actual warehouse loader, target database schema, and database connection have not been verified in the provided files, the procedures and database structures described below are documented as the proposed Stage 3 design rather than confirmed implemented features.

## 1. Load Source and Target Specification

This section identifies the transformed data received from Stage 2 and the target analytics warehouse where the data will be stored.

### 1.1 Load Input

| Item | Description |
| :--- | :--- |
| **Input Source** | Validated transformation handover from Stage 2, consisting of `dim_date` and `fact_daily_summary`. |
| **Format and Location** | In-memory Pandas DataFrames passed directly from the Transformation stage. No intermediate staging tables, CSV files, or Parquet files are required for the normal handover. |
| **Transformation Run ID** | `run_id` from Stage 2 metadata (e.g., `TRN_20261023_100546`). This identifies the transformation execution that produced the data. |
| **Extraction Run ID** | `parent_run_id` from Stage 2 metadata (e.g., `EXT_20261023_100546`). This identifies the original extraction execution from Stage 1. |
| **Batch ID** | `batch_id` from Stage 2 metadata (e.g., `BATCH_20261019`). It identifies the business date being loaded and is passed separately from the output DataFrames. |
| **Batch Window** | One business day in Asia/Manila time (UTC+8), from `2026-10-19T00:00:00+08:00` to `2026-10-19T23:59:59.999999+08:00`. |
| **Handover Status** | Stage 2 decision must be `APPROVED` before automatic loading. A batch marked `MANUAL REVIEW` may proceed only after documented authorization. |
| **Handover Validation** | Stage 2 validation results V-01 to V-11 must accompany the DataFrames to establish that the transformation output passed its acceptance checks. |

#### Stage 2 Output DataFrames
The following tables are the only analytical datasets received by Stage 3:

##### 1. `dim_date` – Date Dimension
| Column | Handover Type | Description |
| :--- | :--- | :--- |
| `date_key` | Integer | Smart date key in YYYYMMDD format. |
| `full_date` | Text (YYYY-MM-DD) | Calendar date represented by the record. |
| `day` | Integer | Day of the month. |
| `month` | Integer | Month number. |
| `year` | Integer | Calendar year. |

##### 2. `fact_daily_summary` – Daily Fact Summary
| Column | Handover Type | Description |
| :--- | :--- | :--- |
| `date_key` | Integer | Unique date identifier and reference to `dim_date.date_key`. |
| `full_date` | Text (YYYY-MM-DD) | Calendar date represented by the daily summary. |
| `total_sales` | Decimal (2 decimal places) | Total daily sales revenue. |
| `total_expenses` | Decimal (2 decimal places) | Total daily operating expenses. |
| `profit` | Decimal (2 decimal places) | Daily operating profit or loss. |

#### Additional Handover Metadata
The following metadata accompanies the two DataFrames but is not treated as an additional DataFrame column:
- `run_id`
- `parent_run_id`
- `batch_id`
- `batch_window`
- `records_read`, `records_output`, `records_rejected`, and `records_excluded`
- `validation_results`
- `decision`
- `code_version`
- `measures`

#### Important Data Contract Rules:
- The `date_key` and `full_date` values must remain consistent between `dim_date` and `fact_daily_summary`.
- `total_sales`, `total_expenses`, and `profit` must be loaded using the values produced by Stage 2. Stage 3 must not recalculate these measures.
- `total_items_sold` is reported in the Stage 2 metadata under measures, but it is not included in the documented `fact_daily_summary` handover schema. Therefore, it is not included as a required column in the proposed warehouse fact table.
- `summary_key` is generated by the warehouse and is not part of the Stage 2 DataFrame.
- `batch_id` and the transformation run ID are supplied through handover metadata and may be recorded in warehouse audit fields.

### 1.2 Target System

| Item | Description |
| :--- | :--- |
| **Target System** | CakeLytics Analytics Data Warehouse |
| **Purpose** | Stores transformed daily business summaries for historical reporting, sales analysis, expense monitoring, profit analysis, and decision support. |
| **Database Management System (DBMS)** | PostgreSQL, hosted and managed through Supabase. |
| **Proposed Target Schema** | `warehouse` |
| **Data Model** | Dimensional model consisting of a date dimension (`dim_date`) and a daily fact table (`fact_daily_summary`). |

The warehouse serves as the analytical destination of the ETL pipeline. It separates reporting data from the operational database and provides structured records that can be used by dashboards and analytical reports.

---

### 1.3 Load Method

| Item | Description |
| :--- | :--- |
| **Load Tool / Technology** | Proposed Python batch loader using Pandas and SQLAlchemy to communicate with PostgreSQL. |
| **Loading Method** | Parameterized database insert and upsert operations. |
| **Batch Frequency** | Daily, after the Stage 2 transformation process has completed and passed its acceptance checks. |
| **Intended Schedule** | 12:00 AM Asia/Manila time for the previous business day, consistent with the intended daily pipeline schedule. |
| **Current Scheduling Status** | Automatic scheduling is not confirmed. Stage 1 is manually executed in Phase 1, Stage 2 is invoked through its test runner in Phase 2, and full orchestration through Prefect is planned for Phase 3. |
| **Write Logic** | `dim_date` uses insert-if-not-exists based on `date_key`. `fact_daily_summary` uses an idempotent upsert based on `date_key`. |

The load process begins only after Stage 2 has completed its transformation and validation procedures. It receives the existing DataFrames and metadata without querying the CakeLytics operational database.

---

### 1.4 Load Scope

| Item | Description |
| :--- | :--- |
| **Tables Loaded** | `dim_date` and `fact_daily_summary`. |
| **Load Order** | First, `dim_date`; second, `fact_daily_summary`. |
| **Expected Dimension Records** | One date record for the target business day. |
| **Expected Fact Records** | One daily summary record for the target business day. |
| **Expected Total Records** | Two DataFrame records per normal daily batch: one dimension record and one fact record. |
| **Load Time Requirement** | Proposed target completion within 60 seconds for the expected daily batch volume. |

The date dimension is loaded first because the fact table references `dim_date.date_key`. This order ensures that the referenced date record exists before the fact record is inserted or updated.

---

### 1.5 Limitations and Assumptions

- **Data Scope:** Stage 3 uses only the `dim_date` and `fact_daily_summary` DataFrames and the metadata handed over by Stage 2. It does not re-extract operational records or repeat Stage 2 transformations.
- **Source Database:** The operational PostgreSQL database in Supabase remains read-only from the perspective of the ETL pipeline. Warehouse writes must be directed to the designated analytics target.
- **Target Schema:** The warehouse schema is proposed and must be created or confirmed in the target PostgreSQL database before implementation.
- **Access Permissions:** A dedicated ETL service account is recommended. It should have only the required privileges to read relevant warehouse metadata and insert, update, or write to the designated target tables. DDL privileges should be restricted.
- **Credentials:** Database credentials and connection strings must be stored in environment variables and must never appear in source code, documentation, or log files.
- **Data Availability:** Stage 3 can load only the business dates and financial summaries delivered by Stage 2. It cannot generate missing historical records.
- **Scheduling:** Automatic daily execution depends on the later pipeline orchestration phase. The proposed schedule must not be described as currently enabled.
- **Warehouse Availability:** The target database must be reachable and have sufficient storage and write permissions before loading begins.

## 2. Target Tables and Column Specification

This section defines the proposed warehouse tables that receive the transformed data from Stage 2.

### 2.1 Target Table Summary

| Table | Type | Primary Key | Foreign Keys | Key Constraints | Purpose |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `dim_date` | Dimension | `date_key` | None | `full_date` UNIQUE, NOT NULL | Stores calendar attributes for date-based reporting. |
| `fact_daily_summary` | Fact | `summary_key` | `date_key` references `dim_date.date_key` | `date_key` UNIQUE, NOT NULL; financial measures NOT NULL | Stores daily sales, expenses, and profit summaries. |

---

### 2.2 Column Specification

#### Table: `dim_date` (Dimension)
* **Purpose:** Stores calendar information used to organize daily financial summaries and support day, month, and year reporting.
* **Table Type:** Dimension Table – SCD Type 0.

| Column Name | Data Type | Key / Constraint | Load Dependency | Reason for Inclusion |
| :--- | :--- | :--- | :--- | :--- |
| `date_key` | INTEGER | Primary Key, NOT NULL | Match Key | Smart date key in YYYYMMDD format used to connect the fact record to the date dimension. |
| `full_date` | DATE | NOT NULL, UNIQUE | Natural Key | Stores the actual calendar date for reporting and date validation. |
| `day` | INTEGER | NOT NULL, CHECK (1–31) | Attribute | Supports daily grouping and analysis. |
| `month` | INTEGER | NOT NULL, CHECK (1–12) | Attribute | Supports monthly reporting. |
| `year` | INTEGER | NOT NULL | Attribute | Supports annual reporting. |

The dimension is static because calendar attributes do not change after they are generated. Existing date records are reused instead of creating duplicate records during reruns.

#### Table: `fact_daily_summary` (Fact)
* **Purpose:** Stores the daily financial summary generated by Stage 2, including total sales, total expenses, and profit or loss.
* **Table Type:** Daily Aggregated Fact Table.

| Column Name | Data Type | Key / Constraint | Load Dependency | Reason for Inclusion |
| :--- | :--- | :--- | :--- | :--- |
| `summary_key` | BIGSERIAL | Primary Key, Auto-generated | Warehouse PK | Provides a warehouse-generated identifier for each fact record. |
| `date_key` | INTEGER | NOT NULL, UNIQUE, Foreign Key | Match Key / FK | Identifies the business date and references `dim_date.date_key`. |
| `full_date` | DATE | NOT NULL | Reference Date | Stores the calendar date associated with the daily summary. |
| `total_sales` | NUMERIC(10,2) | NOT NULL, CHECK (total_sales >= 0) | Measure | Stores total sales received from the Stage 2 handover. |
| `total_expenses` | NUMERIC(10,2) | NOT NULL, CHECK (total_expenses >= 0) | Measure | Stores total expenses received from the Stage 2 handover. |
| `profit` | NUMERIC(10,2) | NOT NULL | Derived Measure | Stores the profit or loss value already calculated by Stage 2. |
| `batch_id` | VARCHAR(64) | NOT NULL | Batch Audit Key | Identifies the Stage 2 business batch responsible for the loaded record. |
| `transformation_run_id` | VARCHAR(64) | NOT NULL | Lineage Reference | Identifies the transformation execution that produced the record. |
| `loaded_at` | TIMESTAMPTZ | NOT NULL, DEFAULT NOW() | Audit Timestamp | Records when the warehouse inserted or updated the fact record. |

> **Important:** The `summary_key`, `batch_id`, `transformation_run_id`, and `loaded_at` fields are proposed warehouse-level fields. They are not part of the Stage 2 `fact_daily_summary` DataFrame. The warehouse generates or supplies these fields during loading using the handover metadata and database defaults.
> 
> The `profit` column must allow negative values because Stage 2 calculates profit as:
> $$\text{profit} = \text{total\_sales} - \text{total\_expenses}$$
> A negative result represents an operating loss and must not be rejected merely because it is below zero.

### 2.3 Keys, Relationships, and Constraints

| Table | Key / Relationship | Specification |
| :--- | :--- | :--- |
| `dim_date` | Primary Key | `date_key` |
| `dim_date` | Unique Key | `full_date` |
| `fact_daily_summary` | Primary Key | `summary_key` |
| `fact_daily_summary` | Foreign Key | `date_key` references `dim_date.date_key` |
| `fact_daily_summary` | Unique Constraint | `date_key` must be unique to maintain one daily fact record per business date. |
| `fact_daily_summary` | Required Columns | `date_key`, `full_date`, `total_sales`, `total_expenses`, `profit`, `batch_id`, and `transformation_run_id`. |

The unique constraint on `fact_daily_summary.date_key` prevents multiple daily summaries from being stored for the same business date.

---

### 2.4 Indexes and Partitioning

| Table | Index | Purpose |
| :--- | :--- | :--- |
| `dim_date` | Primary key index on `date_key` | Supports dimension lookup and fact-to-dimension joins. |
| `dim_date` | Unique index on `full_date` | Prevents duplicate calendar dates. |
| `fact_daily_summary` | Primary key index on `summary_key` | Ensures unique warehouse fact identifiers. |
| `fact_daily_summary` | Unique index on `date_key` | Supports date-based matching and prevents duplicate daily summaries. |
| `fact_daily_summary` | Optional index on `batch_id` | Supports batch-level auditing and recovery. |

Table partitioning is not required for the expected volume of one daily fact record per business date. It may be considered only if the warehouse grows significantly in the future.

---

### 2.5 Reason for Inclusion

The two warehouse tables support the project's analytical requirements:
- `dim_date` provides standardized calendar attributes for daily, monthly, and yearly reporting.
- `fact_daily_summary` provides consolidated daily financial measures for dashboard reporting.
- `date_key` establishes the relationship between the dimension and fact records.
- `summary_key` provides a warehouse-generated primary key.
- `batch_id` and `transformation_run_id` support data lineage, traceability, and rerun management.
- `loaded_at` records when the warehouse receives the data.

The proposed schema contains only the columns needed by the documented Stage 2 handover and the additional warehouse audit fields required by the Load stage.

## 3. Load Strategy and Rules

This section explains how the transformed data is written to the warehouse, how existing records are handled, and how failed or repeated batches are managed.

### 3.1 Load Strategy per Table

| Table | Load Type | Write Logic | Match Key | On Failure |
| :--- | :--- | :--- | :--- | :--- |
| `dim_date` | Incremental | Insert if the `date_key` does not exist; otherwise reuse the existing date record. | `date_key` | Roll back the batch transaction and stop loading. |
| `fact_daily_summary` | Incremental | Upsert using `date_key`; insert a new record or update the existing daily summary. | `date_key` | Roll back the batch transaction and stop loading. |

---

### 3.2 Detailed Write Logic

1. **`dim_date`**
   - The loader checks whether the incoming `date_key` already exists in the target dimension table.
   - If the date does not exist, the loader inserts the incoming dimension record.
   - If the date already exists, the existing record is reused.
   - The loader does not create duplicate calendar dates.
   - Because the date dimension follows SCD Type 0, existing calendar attributes are not expected to change.

2. **`fact_daily_summary`**
   - The loader matches the incoming fact record using `date_key`.
   - If no fact record exists for the date, a new record is inserted.
   - If a record already exists for the date, the existing daily summary is updated with the values supplied by the new approved Stage 2 handover.
   - The warehouse-generated `summary_key` remains the record's primary key.
   - The `batch_id`, `transformation_run_id`, and `loaded_at` fields are updated or recorded according to the successful load operation.

The loader must not recalculate `total_sales`, `total_expenses`, or `profit`. These values are accepted from the Stage 2 DataFrame.

---

### 3.3 Handling Changing and Deleted Data

| Data Situation | Handling Rule |
| :--- | :--- |
| **Existing date dimension record** | Reuse the existing record. No duplicate date is inserted. |
| **Existing daily fact record** | Update the record using the new approved Stage 2 values for the same `date_key`. |
| **New business date** | Insert a new dimension record followed by its corresponding fact record. |
| **Cancelled orders** | Already excluded by Stage 2 rule B-01. Stage 3 does not process them again. |
| **Voided waste logs** | Already excluded by Stage 2 rule B-02. Stage 3 does not process them again. |
| **Voided inventory logs** | Already excluded by Stage 2 rule B-03. Stage 3 does not process them again. |
| **Late-arriving updates** | Handled through Stage 2 reprocessing of the affected business date. Stage 3 then updates the existing fact record using the newly approved handover. |
| **Unexpected handover schema** | Reject the batch before writing if the incoming DataFrame does not match the documented Stage 2 output contract. |

The Load stage does not perform additional business filtering or data cleaning. All such procedures remain the responsibility of Stage 2.

---

### 3.4 Load Order and Dependencies

The following loading order is required:
1. **Load `dim_date`:** Insert the date record if it does not already exist.
2. **Load `fact_daily_summary`:** Insert or update the daily fact record using its `date_key`.
3. **Verify Referential Integrity:** Confirm that the fact record references an existing date dimension record.
4. **Perform Post-Load Validation:** Check the loaded records against the Stage 2 handover before committing the transaction.

The foreign key constraint on `fact_daily_summary.date_key` prevents a fact record from referencing a nonexistent date dimension record. If the required dimension record is missing, the fact load must fail and the transaction must be rolled back.

---

### 3.5 Transaction and Rollback Handling

The proposed loading process uses one database transaction for the entire batch.

#### Transaction Sequence:
1. Begin the database transaction.
2. Insert or reuse the `dim_date` record.
3. Insert or update the `fact_daily_summary` record.
4. Execute post-load validation checks.
5. Commit the transaction if all critical checks pass.
6. Roll back the transaction if a critical check fails or a database error occurs.

This approach ensures that the dimension and fact records are handled as one logical operation. A failed transaction must not leave a partially loaded batch in the warehouse.

Operational failure metadata should be written after the transaction rollback or through a separate logging mechanism so that the failure record is not lost when the data transaction is rolled back.
